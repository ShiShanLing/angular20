# 微信分身（微信2）修改说明

桌面上的 `WeChat2.app` 是微信 4.2.0 的独立副本。只改文件夹名不够：它和 `/Applications/WeChat.app` 的包标识都是 `com.tencent.xinWeChat` 时，重启后登录项先拉起原版，再点分身只会把原版叫到前台。

这次改的是 **2026-10-30** 的桌面副本（版本 4.2.0，构建号 270348），系统是 macOS 27.2。原版 `/Applications/WeChat.app` 没有动。

下次如果用新版微信覆盖了 `WeChat2.app`，按下面重做一遍。不要把说明文件放进 `.app` 里面，放进去会使签名失效。

## 为什么必须改成同样长度的标识

`com.tencent.xinWeChat` 在主程序和动态库里是写死的 ASCII 字符串，长度 **21**。这次一共 84 处，分布在 19 个文件里，没有 UTF-16 副本。`xinWeChat` 也都出现在这句完整标识里，没有拆开的片段。

换成 `com.tencent.xinWeChat2` 会多 1 个字节，Mach-O 里的偏移会错，程序直接坏掉。`org.tencent.xinWeChat` 同样是 21 字节，可以原位替换。

替换时跳过符号链接和 `_CodeSignature`。签名目录会在重签时重建。

含有这句标识、必须替换的文件：

- `Contents/Info.plist`
- `Contents/MacOS/WeChat`
- `Contents/MacOS/WeChatHelper.app` 的 `Info.plist` 和可执行文件
- `Contents/MacOS/XPlayer.app` 的 `Info.plist`、可执行文件、`libxplayercore.dylib`
- `Contents/MacOS/WeChatAppEx.app` 里 Resources 下那份约 412MB 的 `WeChatAppEx Framework`，以及 `libappextld.dylib`
- `Contents/PlugIns/WeChatFileProviderExtension.appex` 的 `Info.plist` 和可执行文件
- `Contents/PlugIns/WeChatMacShare.appex` 的 `Info.plist` 和可执行文件
- `Contents/Resources/` 下的 `wechat.dylib`、`libwechaticon.dylib`、`libxplayer.dylib`
- `Contents/Frameworks/Sparkle.framework` 里的 `Sparkle`，以及 `Installer.xpc` 的 `Info.plist` 和可执行文件

`WeChatAppEx Framework` 在 `Contents/Frameworks` 下还有一份约 1.8MB 的二进制，里面没有这句标识，不用改内容，但后面要跟着重签。

## 重签时权限怎么处理

先取出各组件原来的 entitlements，再改二进制。二进制一改，旧签名就作废，`codesign -d --entitlements` 会失败。

ad-hoc 签名没有腾讯的 Team ID。下面几项留着的话，macOS 27 会在启动时把进程杀掉：

- `com.apple.application-identifier`
- `com.apple.security.application-groups`
- `com.apple.security.app-sandbox`
- `com.apple.security.inherit`

沙箱去掉之后，程序才能用本机签名启动。同时补上这四项，避免动态库和 JIT 被拦：

- `com.apple.security.cs.allow-jit`
- `com.apple.security.cs.allow-unsigned-executable-memory`
- `com.apple.security.cs.disable-library-validation`
- `com.apple.security.cs.allow-dyld-environment-variables`

桌面上的 `WeChat2-entitlements.plist` 只有 `allow-jit`，是更早一次尝试留下的，**不要用它来签**。

不要加 `--options runtime`。硬化运行时配上 ad-hoc，内部动态库容易校验失败。也不要用一次 `codesign --deep` 把同一份 entitlements 套到所有子组件上。

## 验收

原版保持运行时再打开分身，应该同时存在两个主进程：

```bash
pgrep -lf "/Applications/WeChat.app/Contents/MacOS/WeChat$"
pgrep -lf "/Users/SSL/Desktop/WeChat2.app/Contents/MacOS/WeChat$"
```

`codesign -dv` 里应看到 `Identifier=org.tencent.xinWeChat` 和 `Signature=adhoc`。`codesign --verify --verbose=2` 应以 `valid on disk` 结束。

分身的文件目录是 `~/Library/Containers/org.tencent.xinWeChat`。启动参数里的 `--wechat-files-path` 也应指向这里，而不是 `com.tencent.xinWeChat`。

## 这次踩过的坑

- 只改 `.app` 名字、不改包标识：重启前如果原版没开，分身能临时起来；登录项里的「微信」在重启后先占住 `com.tencent.xinWeChat`，分身再点就会唤起原版。
- `Contents/MacOS/XPlayer.app/Contents/Frameworks/vk_swiftshader_icd.json` 会让签名停在 `code object is not signed at all`。它是 SwiftShader 的软件渲染配置，相对路径是 `./libvk_swiftshader.dylib`。把它移到 `XPlayer.app/Contents/Resources/` 后可以签过。硬件渲染不受影响；软件渲染回退可能找不到这个 json。
- 子组件重签之后，必须再签一次最外层 `WeChat2.app`，否则外层密封仍然指向旧签名，`codesign --verify` 会报 `invalid signature`。
- `xattr -cr` 可能在只读的 `gpu_shader_cache.bin` 上报 `Permission denied`。这个警告可以忽略，不妨碍签名。
- 沙箱去掉后，崩溃信息会写到 `~/Documents/app_data`。这个目录 2026-08-19 就有了，是更早一次分身留下的，不是这次新造的。正式聊天文件仍在新的容器目录。
- 自动更新必须关掉。否则 Sparkle 可能把分身盖回腾讯官方签名，包标识也会变回去。
- 协议如果不改，`lsregister` 之后 `weixin://` 可能被分身抢走。

## 不用重做的情况

已经改好的 `WeChat2.app` 重启后直接打开即可，不必再跑脚本。只有整包被新版微信覆盖、或者又出现「一点分身就唤起原版」时，才按上面重做。
